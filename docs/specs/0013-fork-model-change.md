# SPEC-0013: Fork into another model of the same provider

Date: 2026-09-21. Status: implemented; remote CI pending. Local RED/GREEN and native scripted-gateway evidence is in [TDD-0013](../tdd/0013-fork-model-change.md). Origin: an embedding host needs to change an agent's model without losing its native history. The behavior applies to every caller.

## Problem and scope

`sessions.fork` copies the source runtime, so a completed session's native history cannot continue on another model. Each registered provider also pins at most one model: the engine rejects any other task model, and the JSON CLI requires `providers.<name>.model`.

This increment lets `sessions.fork` choose another owner-allowed model under the same registered provider name. Provider name, permission profile, write paths and root task stay those of the source, so no permission boundary is crossed. The history still reaches the new model because the runtime resends it with every request; what the change loses is prompt-cache reuse, so callers must acknowledge that cost explicitly. Non-goals: cross-provider continuity, in-place changes to an existing session's runtime, permission-profile or write-scope changes, model changes chosen by model tools, context checks derived from recorded usage, and Codex model-changing forks before separate native evidence. Event types and cursors, `usage.recorded`, `usage.getRecord`, the Claude adapter's `query`/`createMcpServer`/`inspectSession` injection points and storage configuration do not change.

## Acceptance criteria

- **M01 — Allowed models:** Engine and JSON CLI provider configuration accept `models`, a non-empty list of unique model names. `model` remains shorthand for a one-item list; configuring both is invalid. Task admission, `sessions.open` and every model-changing fork target require a listed model. A model-changing fork also requires the provider to configure `model` or `models`; without a list it fails with `VALIDATION_ERROR`. Removing a model on restart leaves existing sessions unchanged and rejects new tasks for that model.
- **M02 — Fork target model:** `sessions.fork` accepts an optional `model` allowed for the source's provider name. When it differs from the source model, the call must also pass `acknowledgeCacheLoss: true`; otherwise it fails with `CACHE_LOSS_NOT_ACKNOWLEDGED` before any session is created. The new session records the target model and the source session is unchanged. `model` and `acknowledgeCacheLoss` are part of the operation's idempotency payload. The operation result and `session.fork_prepared` report `modelChange: {fromModel, toModel, promptCacheReuse: false}` so hosts can inform end users. An inline `requestedMode: "fork"` keeps the source model, as today. Omitting `model`, or naming the source model, keeps today's fork behavior.
- **M03 — Declared capability:** Adapters declare a typed `forkModelChange` capability. A model-changing fork on a runtime without it fails with `UNSUPPORTED_CAPABILITY` before any session is created. Claude enables it only after M05 passes; Codex keeps it disabled.
- **M04 — Model-dependent checks:** Tasks on the fork must declare the target model (`SESSION_INCOMPATIBLE` otherwise). `contextLimits`, pricing and budget reservation apply to the target model at dispatch, as for any task; a missing price under an active budget yields the existing `BUDGET_PRICE_UNKNOWN`. The engine does not estimate inherited history from recorded usage: Claude records one turn aggregate per dispatch, which overstates history when a turn made several native requests. As with reuse, callers include inherited history in `contextEstimate`; the provider's own context limit remains the final boundary.
- **M05 — Native evidence:** Extend the scripted-gateway smoke with the installed Claude binary. Fork a completed session into a different allowed model and assert at the gateway that the forked request names the target model, its messages contain the source history up to the checkpoint, the returned native session ID differs from the source, and the source session is unchanged. Use synthetic credentials and no paid model. If any assertion fails, `forkModelChange` stays disabled.
- **M06 — Tools and wire:** Bound runtime tools cannot change a model: they fork only through inline routing, which keeps the source model. `SessionForkParams` gains optional `model` and `acknowledgeCacheLoss`. Both SDKs, the schema and generated types change additively, with cross-language tests.
- **M07 — User documentation:** The fork section of the wiring guide states that a fork may change model only within the provider's allowed list and with explicit acknowledgment; tasks on the fork declare the target model; the new model cannot reuse the source model's prompt cache, so the first response after the change reprocesses the whole inherited history and is slower and more expensive, while later responses warm the new model's cache; hosts should tell end users this before switching; and `contextEstimate` must include inherited history.

## Verification

Record RED for M01–M04 and M06 before changing runtime code. Run M05 separately with the native scripted gateway, then the focused tests, generated-contract, type and format checks, and both full suites. No credentials or paid models are used. Publication and pushing remain separate actions.
